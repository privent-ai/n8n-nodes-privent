# Positive corpus — business-shaped prose that DOES carry a value a detector
# should find. One case per line: EXPECTED_KIND | value | sentence.
#
# PROVENANCE. Hand-authored for this repository, in this session, by the
# assistant, for the N4-7b measurement. No line is copied from a customer, a real
# mailbox, a real ticket, or any external dataset. Every value is synthetic:
# addresses use RFC 2606 reserved domains, card numbers are the publicly
# published test PANs, and every other identifier is invented to match a format
# rather than to name a person.
#
# WHY IT EXISTS. Zero false positives is not evidence that a detector works. A
# detector that never fires at all also scores zero, and admitting it would mean
# admitting it for looking harmless. Each detector admitted to `aggressive` must
# also fire on at least one case below. Detectors that fire on neither corpus are
# named as dead weight with a count, not quietly admitted.
#
# One case moved when NP-V landed: the public-IP example used to be
# `203.0.113.42`, which is TEST-NET-3 — a documentation range, now deliberately
# suppressed. A positive corpus that proves a detector alive with a value the
# product is supposed to ignore proves nothing, so it was replaced with two
# genuinely routable addresses.
#
# EXPECTED_KIND may list synonyms separated by '/', e.g. `IP_ADDRESS/IPV4`. Two
# detector names for the same concept are not a mislabelling, and counting them
# as one would reject a correct detector for a naming choice. EXPECTED_KIND is
# the kind the value SHOULD be reported as. A detector that
# matches the value under a different kind is counted as a false positive, not a
# hit: capturing a real value under the wrong kind is the same category
# corruption N4-7a measured, where `hello@privent.ai` was reported as
# SOCIAL_MEDIA_HANDLE and TIKTOK_USERNAME rather than as an email address.
